For an SDET, projects look quite different from normal "JavaScript projects."

You're not primarily trying to prove:

"I can build a website."

You're trying to prove:

"I can understand a software system, identify how it can fail, write automated tests, investigate failures, and build a maintainable automation framework."

So I'd structure your projects as a progression.

1. Tiny projects — where you should start now

These are JavaScript projects, but you deliberately approach them like a tester.

Test Result Analyzer

Input:

const results = [
    { test: "Login", status: "passed", duration: 120 },
    { test: "Search", status: "passed", duration: 80 },
    { test: "Checkout", status: "failed", duration: 230 },
];

Your program produces:

Total tests: 3
Passed: 2
Failed: 1
Pass rate: 66.67%

Failed tests:
- Checkout

Slowest test:
- Checkout (230ms)

You're practicing:

objects
arrays
functions
filter()
map()
reduce()
find()
some()
every()

This is a very good project for your current level because it directly resembles test data.

4. API testing project

This is where your projects start looking much more like actual SDET work.

Eventually:

API
 │
 ├── GET /users
 ├── GET /users/:id
 ├── POST /users
 ├── PUT /users/:id
 └── DELETE /users/:id

Your automation checks:

✓ Status code
✓ Response body
✓ Response structure
✓ Required fields
✓ Data types
✓ Response time
✓ Error responses
✓ Authentication

For example:

POST /users

Expected:
201 Created

Actual:
400 Bad Request

Test: FAILED

Reason:
email field missing

This is a major SDET skill.

5. UI automation project

Then you reach Playwright.

Instead of simply building a website, you'll take an existing application and automate it.

For example:

E-commerce application

        ↓

        Playwright
        │
        ├── Login tests
        ├── Search tests
        ├── Product tests
        ├── Cart tests
        ├── Checkout tests
        └── Negative tests

A test might conceptually look like:

Open application
       ↓
Login
       ↓
Search "laptop"
       ↓
Verify results
       ↓
Open product
       ↓
Add to cart
       ↓
Verify cart

But the important part isn't simply making the script work.

You need to think:

What should happen if the product doesn't exist?

What if the login password is wrong?

What if the network request fails?

What if the button isn't available?

What if the product price changes?

That's where testing knowledge + programming come together.

The important thing

Don't wait until you're "ready for projects."

Your projects should grow with you.

Right now, a 50-line JavaScript test-analysis program is more appropriate than a 2,000-line Playwright framework.

Then, as you learn async/await, you modify your project to use asynchronous operations.

When you learn APIs, you make it consume API data.

When you learn DOM, you give it a UI.

When you learn Playwright, you automate that UI.

When you learn CI/CD, you make the tests run automatically.

So eventually one small project can evolve into a serious SDET portfolio project rather than you throwing away everything you built while learning.
